# Gateway / app-auth performance investigation

Production baseline: `5dbca61`. Production code and app-auth have not been changed during this investigation. The default Edge candidate requires no migration or security-policy update. The optional DB validation candidate below does require a migration and remains disabled.

## Resumed investigation — 2026-10-13

- Fixed a deployment hazard: `validate-session` had been unconditionally switched to a DB function that may not exist on the target DB. It now stays on the existing Edge path unless `PARTNERDESK_SESSION_VALIDATION_DB=true` is explicitly configured after migration and acceptance. This turn did not apply any migration or change any shared DB, policy, account, data or Production deployment.
- Retained request-local exact-JWT verification reuse, browser in-flight validation sharing, gateway Auth/policy overlap, verified gateway IP-policy reuse, parallel profile/consent reads and Ticket list reads, and `icn1` configuration. Login/MFA issuance and logout implementations remain unchanged; only the redundant immediate validation of freshly issued sessions is removed by the existing candidate.
- Further shortened the detail dependency chain: related reads now start immediately after the audited row arrives, without waiting for the independent session validation. Both branches must succeed before UI publication. Company Admin skips the unnecessary assignee organization read; Partner Admin retains it.
- Final validation: `npm test` **159/159**; separate actual Edge contract suite **22/22**; `npm run lint` and `npm run build` passed. Regression tests explicitly cover validation failure preventing detail display, cancelled navigation preventing publication, and the default protected Edge path for all five auth actions. PostgreSQL tests cover IP enforcement, proof forgery/replay, direct business access denial, RLS/role scope, failure audit, data preservation and administrator recovery.
- New Preview deployment attempted with DB validation explicitly disabled and existing isolated `app-auth-perf-candidate`, but Vercel returned **Not authorized**. No new deployment was created. Browser automation also failed during environment initialization, so no authenticated browser session was available for measurement.
- Existing optimized Preview public-policy probe: **HTTP 403**, actual region **icn1**, client **2604.464 ms**, policy HTTP **1160.0 ms**, denial audit HTTP **159.9 ms**, handler **1324.4 ms**, first module request. This measures a denied request on an older Preview, not this final change or successful Ticket/auth performance. The allowlist was not changed or spoofed.

Acceptance remains incomplete. Previously observed Production app-auth **3.50 / 3.59 / 4.08 s**, Ticket list **about 5 s**, detail **about 8 s** have no new successful authenticated comparison. Code-derived per-page gateway counts remain list **5 → 5** (parallelized), assigned Company Admin detail **7 → 6**, Partner Admin detail **7 → 7**, excluding pagination and concurrent initiators. Edge authentication checks are reduced **2 → 1 per request** by request-local reuse, as verified by automated tests; this is not a measured elapsed-time improvement.

Remaining bottlenecks: protected gateway/Auth/policy HTTP latency on each request, Edge profile/proof/session round trips on the default path, detail row → partner relation → organization dependencies, and pagination for larger datasets. Production is not ready for approval until authorized Preview deployment and authenticated allowed-IP measurements establish functionality/security and list ≤2 s/detail ≤3 s. Existing Preview diagnostics can collect numeric durations/counts automatically after ordinary list/detail navigation; no Chrome Network export is required. ## Candidate changes

Optimized Preview: https://partnerdesk-6go7tfic0-716-7c9a.vercel.app, isolated Edge `app-auth-perf-candidate`.

- Vercel Function runs in icn1, matching the Seoul DB. Edge invocations request ap-northeast-2; response region is independently recorded.
- Edge JWT Auth verification is reused only within one HTTP request for the same exact JWT. Proof validation and handler authentication still require that verified identity. A different JWT or subsequent HTTP request is verified anew. No shared identity/policy cache.
- With gateway proof enforcement enabled, avoid the unused legacy IP setting DB read. Current gateway policy evaluation and DB proof/IP verification still run on every request.
- Browser shares only concurrently in-flight identical validate-session requests bound to exact Auth JWT and app-session token. Results are not cached.
- Fresh server-issued password/MFA sessions no longer make a redundant immediate validate-session call. Existing-session restoration and periodic validation remain. Profile and consent reads independently enforce server session/RLS/proof guards and remain mandatory.
- Profile and consent queries start together; Ticket list validation and its four protected reads start together; Ticket detail's audited read and validation start together. Results are shown only after mandatory validation succeeds.
- Company Admin detail no longer reads the assignee's organization solely to decide takeover rights, which Company Admin already has. Partner Admin still performs the original organization check.

## Request graph (code-derived, not a browser measurement)

For one page of each dataset, Ticket list still uses one session validation plus four data requests: five gateway calls. Critical ordering changes from `validation -> four parallel reads` to `five parallel requests`.

Assigned Ticket detail for Company Admin, with at least one partner ID, changes from seven to six gateway calls: validation, audited detail, business, activities, service-partner relations and partner organizations. Partner Admin keeps the extra assignee organization read. Pagination adds further calls. Successful login removes one redundant Edge validation; concurrent validation coalescing may remove more duplicate calls depending on actual initiators.

The complete 32-entry Chrome request trace has not been provided, so all 32 requests cannot be individually classified as necessary/unnecessary. Existing selected Ticket fields and relations are retained rather than guessed to be unused.

## Preview acceptance gate

From the allowed office IP, measure baseline and candidate app-auth/ordinary gateway success (HTTP 200), Ticket list/detail perceived duration and gateway call counts. Read only these response headers: `Server-Timing`, `X-PartnerDesk-Function-Region`, `X-PartnerDesk-Edge-Region`, `X-PartnerDesk-Edge-Auth-Checks`, `X-PartnerDesk-Instance-First-Request`.

Metrics: gateway auth/policy/audit/proof/upstream/response/total; nested Edge e_auth/e_proof_db/e_profile/e_policy/e_session_db/e_total. HTTP timings are not equivalent to query execution time. Never copy request authorization/session headers, PINs or response session tokens into the report.

Production deployment and production app-auth update are prohibited until authenticated Preview functionality and actual performance improvement are demonstrated. Do not restore policy to monitor for benchmarking. Keep proof, RLS, MFA and audit checks. Temporary diagnostic Edge functions must be removed after final acceptance or explicitly kept only while the comparison is pending.
