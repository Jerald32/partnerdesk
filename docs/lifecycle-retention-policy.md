# 보존 및 휴면 계정 검토 정책 — 2026-10-13

## Ticket 최소 보존

모든 Ticket은 신규/진행/보류/완료 상태와 무관하게 기존 `created_at`부터 UTC 달력 3년간 최소 보존한다. 기준은 `created_at + interval '3 years'`이며 완료 시각 `resolved_at`은 기준이 아니다. 윤년을 포함한 달력 계산이므로 Base44의 3×365일 계산과 다르다. 기존 생성일·종료일을 변경하거나 과거 이력을 재작성하지 않는다.

3년 경과는 삭제/익명화 허용 또는 승인이라는 뜻이 아니다. Company Admin 설정 화면의 검토 목록에 표시한다. `retention_state`는 `retained`(계속 보존), `disposal_review`(폐기 검토 요청)를 추가 사용한다. 기존 `active`/`anonymized` 상태를 재작성하지 않는다. 기존 `anonymized` 기록은 되돌리거나 원문을 만들어 복원하지 않는다. 목록은 100건씩 오래된 순서로 조회하며 검토된 Ticket도 상태와 함께 남는다. 검토 결정은 버전 검증 후 감사 로그와 동일 트랜잭션으로 기록한다. `retention_processed_at`은 실제 처리 시각이므로 검토 결정에 사용하지 않는다.

Base44 `processDataRetention`과 기존 Supabase `private.process_ticket_retention`은 상태 무관 3년 경과 개인정보 익명화를 구현했었다. 확정된 새 정책에 따라 private 함수는 처리 건수 0과 `administrator_review_required`만 반환하도록 교체한다. 서비스 RPC도 동일 함수를 호출하므로 더 이상 자동 익명화를 실행하지 않는다. Ticket/Activity/첨부 메타데이터 DELETE 및 TRUNCATE, 새로운 Ticket 익명화·처리 시각 변경도 DB 트리거로 차단한다. 정상 업무 수정·상태 변경은 기존 RPC대로 허용한다. 전체 레코드를 삭제하는 함수나 관리자 폐기 실행 버튼은 이번 단계에 도입하지 않는다.

Ticket과 활동/첨부 메타데이터는 FK로 연계되며 함께 보존한다. 감사 로그의 대상 ID는 논리 연결이므로 Ticket 삭제에 연쇄 삭제되지 않고 기존 불변 저장소 정책을 유지한다. 화면의 Ticket 감사 건수는 `target_type=Ticket`인 기록이며 첨부·관련 조직의 모든 감사 로그 수를 뜻하지 않는다. 실제 Storage 파일 수명과 다운로드/삭제 증적은 아직 별도 구현·검증 대상이다. DB 소유자가 트리거를 제거하는 등의 권한 있는 우회까지 외부 불변 보관과 동일하게 보장하지 않는다.

## 폐기 절차 설계 — 실행 미구현

1. 보존기간·진행 중 업무·법적 보존 사유를 관리자에게 제시한다.
2. 관리자는 현재 보존 유지 또는 폐기 검토 요청만 기록한다.
3. 후속 구현에서 별도 승인자, 승인 범위/근거, 첨부 Storage 처리, 개인정보 법적 근거, 연관 데이터 영향 및 복구/보류 조건을 확인한다.
4. 승인과 실제 실행은 분리하고 각각 서버 감사 및 폐기 증적을 남긴다. 본 단계에는 승인된 실제 폐기 실행 경로가 없다.

## 휴면 계정

기존 `profiles.last_login_at`은 app-auth의 업무 세션 발급 시 서버에서 갱신된다. 비밀번호 입력만 성공하거나 MFA가 실패한 시각을 로그인 성공으로 간주하지 않는다. 관리자 접속 현황은 이 값과 기존 `private.app_sessions.authenticated_at`의 최대값을 사용한다. 페이지 로드나 세션 heartbeat를 마지막 로그인으로 저장하지 않는다. 과거 성공 로그가 없으면 “확인된 로그인 없음”으로 표시하며 휴면 검토 계산에만 계정 생성 시각을 사용한다. 계산을 위해 로그인 시각을 임의 생성하지 않는다.

Base44 `checkInactiveAccounts`는 Partner에 23일 경고/30일 자동 정지를 사용했지만 새 기준이 미확정이므로 이 값을 복원하지 않는다. `system_settings.dormancy_review_days`는 기본 빈칸(미설정)이며 Company Admin이 1~36500일 또는 미설정으로 저장할 수 있다. 값은 검토 후보 식별에만 사용한다. 자동 잠금 작업은 구현/활성화하지 않는다. `dormancy_auto_lock_enabled=false`, `ticket_auto_disposal_enabled=false`가 기본값이며 UI나 RPC에 활성화 경로가 없다.

모든 Company Admin과 기존 `inactive_check_exempt` 계정은 자동 잠금 제외로 표시한다. 기존 본인 비활성화 금지 및 마지막 활성 Company Admin 보호를 유지한다. 비활성화·재활성화는 기존 조직 범위 검사와 감사 RPC를 재사용한다. `reactivate_profile`은 기존 suspended뿐 아니라 disabled도 복구하며 역할·조직을 유지한다. Guest는 복구 후에도 업무 권한을 얻지 않는다. 상태 변경 시 기존 세션 철회를 유지하며 Ticket/활동/감사 로그는 삭제하지 않는다.

## 미확정 정책

- 개인정보의 목적별 최소/최대 보존기간은 Ticket 업무 기록 최소 3년과 별개다. 개인정보 삭제 요구와 법적 업무 기록 보존의 충돌, 비식별화 가능 필드 및 절차를 확정해야 한다.
- 감사 로그의 최소/최대 보존기간, 외부 백업 및 actor 개인정보 처리 기간은 미확정이다. Ticket 3년 규칙을 감사 로그에 적용하지 않는다.
- 휴면 기준 기간·경고/알림·자동 잠금 도입 여부는 별도 승인 대상이다. 현재 기준 설정은 수동 검토만 지원한다.
- 폐기 승인 권한 분리, 법적 보류, 실제 첨부파일 처리 및 운영 백업 정책은 후속 결정 대상이다.
- 기존 Base44의 별도 워크플로는 독립 앱 DB 보호 범위 밖이며 독립 앱에 새 cron을 등록하지 않는다.

MFA/IP 설정은 변경하지 않는다. 기존 관리자·조직·Ticket·동의·세션·감사 이력은 보존한다.

## 적용 및 검증

신규 migration `20261015000000`만 dry-run 후 적용했다. 적용 전후 사용자·조직·Ticket·Activity·첨부 메타데이터·동의·업무 세션·기존 감사 로그의 집계 해시가 일치했고 기존 감사 체인 23건이 정상이다. Company Admin 1명, `mfa_enabled=false`, 휴면 기준 미설정, 자동 잠금/폐기 비활성을 확인했다. app-auth Edge v6의 기존 업무 세션 발급 경로를 재사용하므로 Edge 변경·재배포는 필요하지 않다.

앱 테스트 127개와 Edge 테스트 21개(148개), lint, build 통과. 테스트에서는 모든 Ticket 상태의 보존 검토, 실제 삭제/익명화 차단, 역할/세션 검사, 비활성화·복구, 감사 실패 시 상태 변경 롤백을 확인했다. 실제 운영 관리자 화면의 사용 실증 및 종합 검증은 별도 수행 대상이다.
